# AIEHLC Project Architecture

AIEHLC (AIE High-Level Compiler) is a compilation/deployment solution for AMD Versal AI Engine. It has **two parts**:

1. **aiehlc** — Clang-based tool that compiles C++ (AIE driver C API) into host + kernel binaries for single-kernel AIE apps.
2. **tilinglinalg** — MLIR progressive lowering pipeline that offloads a GEMM operation across multiple AIE tiles, generating host, kernel, and routing C++ code through 6 custom dialects.

Both share the AIE runtime (`include/aie_runtime.h`) and target Versal AI Core Series with pre-built PDI.

```
├── example/                   # AIE examples (perf, matmul, multi-kernel)

```

## Part 1: aiehlc (Single Kernel)

Compiles a user C++ file into a host ELF (ARM) + kernel ELF (AIE core):

```
User C++ → aiehlc (Clang AST) → AieFrontEnd (MLIR)
  → Kernel: xchesscc → xchessmk → kernel ELF (embedded in host via ld -r -b binary)
  → Host: aarch64-g++ (host.cc + aie_runtime.c + routing + kernel.o) → host ELF
```

Key runtime API: `__Runtime_device_init`, `__Runtime_load_kernel_group`, `__Runtime_launch_kernel_group`, `__Runtime_dma_bd_config`, `__Runtime_wait_event`, `__Runtime_device_teardown`.

Platforms: baremetal (`aarch64-none-elf-g++`) or Linux (`aarch64-linux-gnu-g++`).

## Part 2: tilinglinalg (Multi-Tile GEMM)

### Six Custom MLIR Dialects

| Dialect | Purpose |
|---------|---------|
| **routing** | Abstract tile arrays, data IO, broadcast, mesh partitioning |
| **routinghw** | Physical tiles, stream switch ports, packet flows |
| **dmap** | Logical dataflow: ports, streams, push/pull |
| **dmaphop** | Physical hops: tile-to-tile paths, DMA, buffers |
| **dfscheblueprint** | Schedule blueprint: transfer manifests, flow configs |
| **dfschedule** | Executable schedule: DMA BD, kernel launch, locks |

### Pass Pipeline

**Shared stages** (produces dfscheblueprint IR, then module is cloned):

1. `RoutingUnrollingLowerPass` — unroll abstract routing into per-tile ops
2. `RoutingToDmapPass` — routing → logical dataflow
3. `DmapToDmaphopPass` — logical → physical hops
4. `DmaphopTodfscheblueprintPass` — hops → schedule blueprints

**Host path** → `host.cc`:

5. `BlueprintToSchedulePass` → `ScheduleCanonicalizePass` → `DfscheduleToApiPass` → `RoutingConstantFoldPass` → `CanonicalizerPass` → EmitC → `host.cc`

**Kernel path** → `kernel.cc`:

5. `BlueprintToScheduleKernelPass` → `DfscheduleToKernelApiPass` → EmitC → `kernel.cc`

**Routing path** (alternative, Path A) → `routing.cc`:

1. `RoutingUnrollingLowerPass` → `RoutingLowerPass` → `RoutingHWLowerPass` → `RoutingDeadArgPass` → `RoutingConstantFoldPass` → `CanonicalizerPass` → EmitC → `routing.cc`

### Routing Implementation (`pass/routingimplement/`)

- **RoutingTopology**: Gen2 AIE tile topology model
- **RoutingPath**: BFS path finding (priority: Memory > SHIM > Core)
- **ResourceManager**: Tracks link/port usage to avoid conflicts

## Build

```bash
# Main aiehlc binary
mkdir build && cd build && cmake .. -DLLVM_INSTALL_DIR=/path/to/llvm/build && make -j$(nproc)

# TilingLinalg unitest (standalone)
 source script/aiehlc.sh --aie-version 5 --runtime-source-file ./example/tileprogram/ccode/simplematmul2.cc
 python3 ./script/test/apppaltest.py -y  -nonreboot > ./applog 2>&1
```

Each dialect has `td/` (TableGen), `gen.sh` (runs mlir-tblgen), and `inc/` (generated .inc files).

- **[src/tool/debug/aiegdb.py](src/tool/debug/aiegdb.py)** — GDB-like scoped CLI frontend over `aiedbg` for live AIE debug. Stateful REPL keeps a *current scope* (partition → tile → channel); `target tile 0 0` / `tar tile(0,0)` and `target channel mm2s0` descend levels and the prompt/breadcrumb changes (`partition(startcol=3)/tile(0,0)/mm2s0>`). Commands default to the current scope: tile scope auto-injects `phys_col=col+startcol`, `row`; channel scope also auto-injects `dir/ch`. Imports `aiediag.py` as a library (offsets, `run_aiedbg_reg_read`, decoders, provenance) and shells out to `aiedbg -d <device>` for raw passthrough (unknown tokens pass through verbatim). Channel helpers: `dma status`, `bd` (JSON BD chain + live HW lengths), `event` (DMA start/finish/error), `dma counter` (AIE performance counters — reads MEM-module `0x11020/0x11024` on core tiles, PL-module `0x31020/24` on shim; decodes CONTROL0 start/stop event ids). Read-only by default; the only write is the explicit `dma counter setup [finished|started]`. `--dry-run` prints every `aiedbg` command without a board; `-c "cmd; cmd"` / `--script FILE` run non-interactively. **`COMMAND_SPEC` is the machine-readable grammar** (module-level dict keyed `universal`/`partition`/`tile`/`channel`, built via the `_cmd()` factory; each entry carries `name`, `aliases`, `args`, `summary`, `intrusive` = writes HW, `passthrough` = forwarded raw to `aiedbg`). It exists so front-ends never hand-copy the grammar: the `spec` verb prints `{scope, spec}` as JSON, `scope_name()` returns the bare COMMAND_SPEC key for the current level, and `_commands()` (the `?` listing) is *rendered from* the spec rather than hand-written, so a command added in one place appears in the CLI listing, the browser autocomplete and the daemon endpoint at once. Note `_commands()` formats as `f"  {sig:<36}  {summary}"` — the two trailing spaces are explicit, not padding, because the browser splits on that gap. Unknown verbs still fall through to `aiedbg` passthrough, so a command missing from `COMMAND_SPEC` works but is not suggested
- **[src/tool/debug/aiemcp.py](src/tool/debug/aiemcp.py)** — MCP (Model Context Protocol) server exposing `aiegdb` live AIE debug to Claude Code. A *third* front-end onto the same `AieGdb.run_line` dispatch (browser/daemon is the other; see `doc/design/aiegdb_live_debug_framework.md` §11): imports `aiegdb.AieGdb` **in-process** and keeps ONE long-lived instance so scope (partition → tile → channel) persists across tool calls. Tools: `aie_exec(cmd)` (primary — run any command line, e.g. `target tile 0 3`, `target channel mm2s0`, `dma status`, `bd`, `pc`), `aie_scope()` (`where`), `aie_commands()` (`?` — per-scope command discovery), `aie_help()` (`help`). Critical: FastMCP stdio uses fd 1 for JSON-RPC and `_passthrough` runs `aiedbg` uncaptured, so `_run()` does OS-fd-level `dup2` capture of fd 1/2 around `run_line()` (a lock serializes it) and traps `SystemExit`/`Exception` so a missing `aiedbg` never kills the server. Config via env (`.mcp.json`): `AIEDBG_TARGET`, `AIEMCP_DEVICE/STARTCOL/AIE_VERSION/JSON_DIR/DRY_RUN`; unset startcol/aie_version auto-resolve from provenance JSON. Registered as `aiegdb` in repo-root `.mcp.json`. Needs `pip install "mcp[cli]"`; smoke test `AIEMCP_DRY_RUN=1 mcp dev src/tool/debug/aiemcp.py`. **LLM-tab auto-connect:** the daemon (`schedule_debug_server.py`) no longer relies on cwd `.mcp.json` discovery — `DebugState._write_mcp_config()` writes a temp `.mcp.json` embedding the daemon-resolved HW config (`AIEDBG_TARGET/AIEMCP_DEVICE/STARTCOL/AIE_VERSION/JSON_DIR`, `command=sys.executable`) and `_llm_spawn` passes it via `--mcp-config <temp> --strict-mcp-config --allowedTools mcp__aiegdb__aie_{exec,scope,commands,help}`; a startup probe (`probe_mcp`, on by default, `--no-mcp-probe` to skip) verifies the connection and prints `LLM MCP: aiegdb connected/NOT connected` (warns without aborting on failure); the temp config is unlinked on Ctrl-C shutdown. **Session gate:** `_run()` calls `_session_refusal(line)` before touching the device. `_needs_hw()` classifies the verb against `_NO_HW_VERBS` (navigation/help/`channels` are always allowed; note `tile 0 0` navigates but `tile list` is a passthrough and *is* gated), then the daemon's `backend_status.json > session.authorized` decides. Unauthorized hardware commands return `{refused:true}` with text telling the model nothing was read and not to infer board state. With no `session` key in the status (aiemcp run standalone from a shell, no UI to gate against) the gate is skipped
- **[src/tool/debug/schedule_debug_server.py](src/tool/debug/schedule_debug_server.py) — session provenance** — The daemon resolves `self.target` at startup from `--target` → `$AIEDBG_TARGET` (exported by `script/test/envlocal.sh`) → `~/.aiedbg_env`, so **a configured target proves nothing about whether this session ever reached the board**. Historically every consumer answered "are we connected?" with `bool(self.target)` (true from process start) and `_write_backend_status()` set `backend="hardware"` as the not-simulator fallback, so the LLM was told `Backend: hardware, target=…` on every message and would read a reachable board still holding a *previous* run's registers and report it as the current run. `DebugState` now tracks `_session_started_at`, `_hw_session` and `_last_run`, with four states surfaced by the single builder `session_state()` / `session_summary()`: `none` (default) → `connected` (a `/ping` probe passed — "Connect") → `attached` (`POST /attach`, "Open Current Session": the user adopted a run started *outside* the UI, so prior board history is explicitly unknown — deliberately NOT folded into `ran`) → `ran` (`start_run` — only here may live state and the applog be treated as current). `hw_authorized()` gates `/grid`; the aiegdb console stays ungated because navigation/`help`/`?` are useful offline and reads fail gracefully. `applog_provenance()` classifies the applog `current`/`predates_session`/`foreign`/`absent` by mtime vs session start — needed because `applog` is a fixed repo-root path the manual CLI flow also writes, which is how a stale `PASS: all N elements match` gets read as the current run. Provenance is published into `backend_status.json` (`session`, `session_summary`) so the out-of-process MCP servers can gate without a round-trip, injected into every LLM message by `_llm_backend_context()` (the hardware branch previously reported no run state at all — the simulator branch always did, and that asymmetry was the core bug), and enforced in the system prompt by a mandatory precondition block above the "go read the hardware" instruction. Also serves `GET /aiegdb/spec` (from the imported `aiegdb.COMMAND_SPEC`, not the subprocess, so autocomplete populates before any command runs or a board exists). **App location** rides the same channel for the same reason: `app_paths()` resolves the four places an app lives — `app_dir` (the app root, where sources and the host ELF are), `bundle_dir` (`<app>/worklocal`, the generated provenance JSONs, i.e. `self.workdir`), `work_dir` (`<app>/Work`, the aiecompiler tree, via `_resolve_work_dir`) and `elf` — because the LLM was previously told only `Working directory: {self.workdir}`, which is the *bundle*, a subdirectory containing no sources, leaving it unable to find the app at all. It is published as `backend_status.json > app_paths`, spelled out with per-path roles in the system prompt's `Where this app lives on disk` block, and appended to every `_llm_backend_context()` line as `App: <id> at <app_dir> (Work/: …)` — the per-message copy is load-bearing because `select_app()` can swap the app mid-conversation while the system prompt is only sent on the first turn

The band equals what the surrounding code already reserves (`streamMaxX/Y = OX_STEP*(N-1)/2`), and `OX_STEP`/`OY_STEP` are now derived from the flow count so the fan stays ~40% of the tile pitch (`COLSTEP=172`, `ROWSTEP=72`) — at a fixed 5px, 12 flows would span 55px of a 72px row. `edgeCanonKey`/`edgeFlows` are retired with it
- **[src/tool/debug/schedule_view.py](src/tool/debug/schedule_view.py) — pane names + empty tile selection** — Each quadrant carries a `.pane-title`: **AIE Debug** (top-left, the existing `h1`, 15px→17px), **Run** (bottom-left — app/board selection, run buttons, applog tail), **Info** (top-right, the tile/net detail panel) and **Tools** (bottom-right — aiegdb/LLM/Search). The names are load-bearing for the **embedded agent**, which must turn "the Info pane" into a tool call, so they are published in three places that all name the same four panes: the LLM system prompt (`_llm_system_prompt`) as a pane → contents → *which tool answers it* table plus a per-pane breakdown; `list_panes()` in `debug_ui_mcp.py`, which prints the window layout before the `get_pane` ids and tags each id with its pane (`tile.hi` → "Info pane (top-right), tile High tab"); and the `debugui-tools` skill, with the same table and a pane column on its `get_pane` reference. Writing that block corrected two stale claims the prompt had carried since before the layout settled — run controls documented as *top-right* (they are bottom-left) and Device Map as a *right-panel tab* (it is a view of the top-left pane) — alongside the board-per-run and Scan/live semantics. `UISTATE` gained `view` (`"grid"`|`"map"`), pushed by `switchView()`, because `get_ui_state()` otherwise could not say which view of the top-left pane the user was on. Separately: the device map draws the whole array including tiles absent from `DATA.tiles`, and the click handler's `if(match) select(...)` had no else — so clicking an info-less tile highlighted it while leaving `panelItems` untouched, and the Info pane went on showing the PREVIOUS tile's detail as though it belonged to the one just clicked. `panelClearTiles(note)` now drops the `tile:` entries and renders `tile (c,r) — no schedule info`; `net:` entries survive (separate selection) and ctrl+click needs no change since adding an info-less tile correctly adds nothing
- **[src/tool/debug/schedule_view.py](src/tool/debug/schedule_view.py) — scan controls** — Grid (`#overlayctl`) and Device Map (`#devmap-scan`) share one selection through `LIVE.what`, and the three controls are meant to be distinct verbs: mode pills select, `Scan` reads once, `live` re-reads every 2s. Picking a mode used to fire `scanOnce(true)` immediately, and the Grid strip additionally set `liveToggle.checked = true` + `setLive(true)` — starting a 2s board-poll the user never asked for. Both pill strips now go through one handler, `pickOverlayWhat(w, setMsg)`, which scans only when `LIVE.enabled`; with live off it moves the selection, calls `dmClearStatus()` (stale DMA tints under a `Cores` selection read as data that was never read) and reports `click "Scan" to read <mode>`. `scanOnce()`'s finally-block retry is gated to match — `LIVE.rescan || (LIVE.enabled && what !== LIVE.what)` — so a swallowed click still retries but a mode changed mid-scan does not re-read the board with the poll off. - **[src/tool/debug/schedule_view.py](src/tool/debug/schedule_view.py) — LLM tool-call rendering** — The daemon emits tool activity as line markers wrapped in blank lines (`\n[tool: <name> <args>]\n`, `\n[tool result: …]\n`) and `.llm-msg` is `white-space:pre-wrap`, so each call cost three lines, its result three more, long args wrapped further, and the result never paired with its call. `llmProse()` now collapses a run of those markers (blank lines included, leading blanks popped off `outLines`) into one `.llm-tools` block holding one `.llm-tc` flex row per call: `.tn` name via `llmToolName()` — strips the `mcp__<server>__` prefix, splits `snake_case`+`CamelCase`, sentence-cases and upper-cases known acronyms from `LLM_ACRONYM` (`aie_exec`→`AIE exec`, `get_ui_state`→`Get UI state`), rendered in the sans stack while values stay monospace; `.ta` args via `llmToolArgs()` — JSON-parsed into one background-filled `.tg` chip per key (label + value side by side, values >60 chars ellipsised, raw-text fallback when the parse fails, no chip border since it would grow the row); and `.tr` folding the result onto the same row (`✓ 41 lines` / `✗ error` / `…` in flight); the left border is grey→accent→red by state and `white-space:normal` on the block escapes the bubble's pre-wrap. `_llm_handle_event` supplies the tag not the payload — `len(result_text.splitlines())`, `empty`, or `error` from the tool_result block's `is_error` — because results run to register dumps. **Pairing is FIFO**: Claude issues tools in parallel batches, so the stream is N calls back to back then N results, never strict alternation (confirmed in `llm_*.log`: two `TOOL CALL` lines, one `TOOL RESULT`, two more calls, then three results). Filling the LAST unresolved row left every earlier call stuck on `…` and the surplus results orphaned into nameless rows that rendered as a tool literally named "Tool"; each result now fills the FIRST unresolved call, and a result with no open call (its call split into an earlier block by prose) renders as a `↳` continuation row. Two parsing details: `LLM_TOOL_CALL` takes the LAST `]` on the line because a JSON list in the args embeds one, and the name stops at whitespace *or* `{` so `name{…}` parses like `name {…}`. `_llm_tool_args()` truncates each VALUE (80 chars, 8 keys) rather than the finished string, so what reaches the browser is always parseable JSON — the previous whole-string 200-char cut produced fragments that could never render as chips. **Ordering constraint:** block HTML is restored in `llmRenderText` *after* `llmColorizeMarkers()`, not inside `llmProse()`, so `_llmBlocks` is render-scoped (reset at the top of `llmRenderText`); the colorizer's file-path regex was otherwise rewriting the inside of a row's `title="…"` and its injected `<span class="llm-file">` quotes terminated the attribute. The old inline `[tool: …]` / `[tool result]` colorizer rules and their `.llm-tool`/`.llm-toolname`/`.llm-toolresult` CSS are retired by the block form
- **[src/tool/debug/schedule_view.py](src/tool/debug/schedule_view.py) — context pills placed inline** — "+ Add context" parked every selection in a row above the input and prepended them all on send, so the blocks vanished from the transcript once drained and there was no way to say *where* a snippet belonged. The prompt box is now a **`contenteditable` div, not a `<textarea>`** — a textarea cannot hold elements — and the pills are real chips inline in the message at the caret; the separate `#llm-ctx-pills` row is gone. Each chip is `contenteditable="false"`, carries `data-cid` into `ctxSnippets`, and has an `×`. Chips **select/copy/cut/paste like text**: only `.mp-x` keeps `user-select:none`, `copy`/`cut` write both a plain-text flavour through the shared walker (`[[label]]`, never the `×` glyph or the ZWSP scaffolding) and an HTML flavour so pasting back rebuilds a real chip, and `paste` reconstructs chips from `data-cid` while turning **everything else into plain text** — parsed with `DOMParser` (inert document) not `innerHTML`, so a pasted `<img onerror>` neither loads nor fires; a chip whose snippet is gone degrades to its `[[label]]`. Newlines on paste are the fiddly part because a copy out of a contenteditable comes back wrapped: a break is emitted BEFORE a block and never after (one after each block added a trailing blank line per wrapper), and a chip is inline text that must never start or end a line of its own — `dropNl()` removes a break the wrapper put immediately before a chip and `justPill` swallows the one that follows, while an explicit `<br>` is user intent and always stands. Three things make the caret behave: (1) a `selectionchange` listener remembers the last range inside `#llmin`, because selecting text in another pane moves the document selection out of the box, so at click time there is no live caret — this is why chips used to land at the end regardless of where you were typing; (2) chips are flanked by **zero-width spaces** so the caret has a text position on both sides (without them the browser cannot place a caret before a leading chip or between two adjacent ones), stripped by the reader; (3) Backspace/Delete are intercepted so a chip goes in ONE press — the browser would eat the flanking ZWSP first and the press would look like a no-op — with only that ZWSP counting as "nothing in between", so a space the user typed is deleted first. `ctxReadInput(pill)` is the one walker that reads the box back, the `pill` callback deciding what a chip becomes — the full `[context from …]` block for the outgoing prompt, `[[label]]` for the transcript echo and the has-anything-to-send check — normalising `<br>`/browser-made blocks to newlines and the post-chip `&nbsp;` back to a space. Switching the tag sprang a trap worth remembering: the device map's capture-phase Space handler (page-scroll suppression) exempted typeable focus **by tag name** (`INPUT`/`TEXTAREA`), so once the prompt box became a `div` every space typed into it was eaten — and only in Device Map view, the default. It now also tests `ae.isContentEditable`. The editable box needs three things a textarea gave free: Enter intercepted to send with **Shift+Enter** via `insertLineBreak` (the browser otherwise builds `<div>` soup), **paste forced to plain text** (default pastes markup, so copying from the transcript injects spans), and no `autoGrow` — it self-sizes, with an `input` listener re-pinning via `llmKeepBottom`. `llmSend(prompt, fromInput)` gained the flag because the box is the source of truth: only an interactive send drains it, so a programmatic caller cannot drain a half-written message. The **auto DMA-scan alert is gone** — `_updateIssueBar` used to fingerprint the issue set (`_issueAlertSent`) and auto-send `[auto] DMA scan detected N issues…` while switching to the LLM tab unprompted; it now only renders the issue bar, and asking the model is the user's call. Labels are deliberately no longer renumbered on delete — collapsing `#1/#2` back to bare is fine for a chip but would orphan a token already sitting in the user's message, which is why `ctxDisplayLabels()` was retired. `llmAddSentCtx()` echoes what went out as read-only pills above the `you` bubble (`.llm-msg-sctx`), click-to-expand the exact text; the prompt is echoed with tokens intact so the expanded blocks don't bury the question.
- **[src/tool/debug/schedule_view.py](src/tool/debug/schedule_view.py) — LLM transcript bottom-pinning** — `#llmmsg` is `flex:1 1 0` in a column shared with `#llmthink`, `#llm-ctx-pills` and `#llminline`, so any height change in those siblings shrinks the transcript while its `scrollTop` stays put — a view pinned to the bottom loses exactly that many pixels off the end (15px each time the think dots appear). `llmKeepBottom(mutate)` captures `atBottom` using the same `< 60` threshold as the append path, runs the mutation, then re-pins; reading `scrollHeight` *after* the mutation forces the reflow so it scrolls against the new geometry. - **[src/tool/debug/schedule_view.py](src/tool/debug/schedule_view.py) — LLM tab working indicator** — `/llm/poll`'s `active` flag is the authority for "the model is working": the daemon sets `_llm_active` when the prompt is written to the `claude` subprocess and clears it ONLY on the stream's `{"type":"result"}` event, so it spans tool calls, tool results and every text block of the turn. `llmPollOnce()` was instead hiding `#llmthink` on the first data chunk (`if (r.data && LLM.pendingId){ llmShowThink(false); … }`), so the dots vanished the instant the opening tokens landed and the remaining minutes of tool work looked idle.
