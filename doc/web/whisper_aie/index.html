1. Two routes to the AIE

The branch took Whisper to the AIE twice. The first route uses the aiehlc compiler end to end and proves that every layer can be expressed and compiled; the second is a hand-written engine that actually runs on the board.

Route A was the feasibility study: it found and fixed four aiehlc bugs that only show on non-square meshes or non-GEMM layers, and added aie::RowSpace (details in GAP_ANALYSIS.md). Its per-launch cost model — full array programming at ~350 ns per register write, fp32 scalar kernels, a batch of one per attention head — would put the encoder in the seconds. Route B keeps aiehlc's runtime, build flow and fabric, and replaces the per-launch compilation model with a persistent engine. The rest of this page describes Route B.

2. What runs where on the array

The device has 36 columns × 4 rows of AIE cores. The engine uses one 5-column partition (absolute columns 2–6):

Since the FC1 → FC2 hand-off moved on chip, the partition is 11 columns wide. Columns 5–10 (relative) add 12 storage memory tiles. They have no east/west stream ports, so they are reached through the shim row (§8).

TilesCountRole
Cores, rows 3–6 × cols 3–616all arithmetic: GEMMs, attention, folded LayerNorm, GELU, logits
Memory tiles, row 1 (MT_A)4one per mesh row: holds that row's activations (and the op headers); broadcasts them along the core row
Memory tiles, row 2 (MT_B)4one per mesh column: holds that column's weights (or an attention head's K/V); broadcasts them up the column

The fabric (fabric/routing.cc) is the 4×4 routing aiehlc generated for conv2dstem, reused by the ResNet engine, with the memory tiles spliced into every input path by hand: shim → MT_A → core row, shim → MT_B → core column. Outputs leave each core as packets and merge per mesh row into one shim S2MM channel.

3. How one operation runs

Every operation — a GEMM pass or an attention round — follows the same protocol (eng/we_desc.h, eng/we_host.h, eng/kernel.cc):

  1. Header. The host writes an 8 KB header per op: op code, shape (row blocks, column tiles, K chunks), flags (bias, GELU, residual, LayerNorm fold, KT/V tile output, row-major, logits) and the parameters of the op's output columns (bias / folded LayerNorm constants, fp32).
  2. Fill. The shims stream the header and the activations into MT_A (block-major, 64 rows at a time) and the weights into MT_B (one panel per output tile group). Memory-tile locks per block let the cores start on block 0 while DDR still delivers the rest.
  3. Replay. MT_A replays each 64-row A block once per output tile; MT_B replays each weight panel once per row block. The DDR is read once per op.
  4. Core self-configuration. Each core reads the header and programs its own tile DMAs (S2MM ping/pong for A and B, MM2S for output packets) with aie_kernel_runtime.h encoders — no host register writes to the 16 cores.
  5. Compute and output. 64×48 output blocks, K in chunks of 48, then the epilogue (folded LayerNorm, bias, GELU, residual, one bf16 rounding). Each block leaves as a 6 KB packet; the shim drops it at the right DDR address with out-of-order BDs.
  6. Overlap. The host queues sub-op s+1 while s runs, and writes the next op's memory-tile BDs into the bank the running op is not using. Only the output BDs are re-armed between ops.

The 16 KB program memory of an AIE2PS core cannot hold the GEMM path and the attention path together, so kernel.cc is compiled twice (WE_PROG=1 GEMM, WE_PROG=2 attention). Between a GEMM op and an attention op the host swaps programs with the control-packet ELF load (~47 µs, 8 swaps per encoder).

6. Numerics: why the transcript matches

we_model.py is a PyTorch model of the engine's exact rounding points. It is run before every board change; it produced the engine's goldens and showed which precision choices keep the transcript.

  • bf16 storage, fp32 accumulation. Every tensor between ops is bf16; every product accumulates in fp32 in the mmul accumulators; each op rounds once.
  • LayerNorm folded into the next GEMM. With W′ = γ⊙W, c = ΣkW′ and d = b + βWT: y = rstd·(xW′T − μc) + d. The core takes μ and rstd from the A chunks it already receives (fp32 sums of x and x²), and applies −μc and the rstd scaling on the multiplier as hi/lo bf16 products. The LayerNorm op and its DDR round trip disappear, and the normalised x is never rounded to bf16.
  • Softmax in exp2 with an integer reference. log2e/√d is folded into Wq. Scores are computed as S − m directly in the accumulator; m is the row maximum of the first chunk rounded up to an integer, raised only when a score passes it by 32, so rescaling O and l is exact exponent arithmetic.
  • Exact GELU. erf-GELU of the bf16 input, from a 1280-entry table for every bf16 value with ⅛ ≤ |x| < 4 (gen_gelu_lut.py), closed forms outside.
  • hi/lo decoder weights. bf16 decoder weights turned step 14 (" ask" vs ",") into a coin flip. Every decoder GEMM, the cross K/V and the logits carry W ≈ Whi + Wlo; the A operand is replayed twice. The token embedding is recovered as (hi+lo)/γ from the logits weight, so it is stored once.

Result: the transcript matches PyTorch token for token — "And so my fellow Americans ask not what your country can do for you ask what you can do for your country." The board prints every step's top-2 logit margin (WHISPER step N: … margin) so a near-tie is visible before it flips.

8. Performance and where the time goes

Measured limits

  • Host register writes cost ~350 ns each on this board, a read ~400 ns, and re-typing the aperture as Device-nGnRE does not change it (probe m7). The host writes only the BD words that changed and prepares each op while the previous one runs, so host time is now hidden almost completely.
  • DDR delivers ~10.5 GB/s read, ~10 GB/s write, ~8 GB/s mixed for the whole array (probe m4); see the floor above.
  • GEMM inner loop: 1251 cycles per 64×48×48 chunk on the board (576 ideal); epilogues add ~18 % of core time.
  • Attention: ~2.1 ms per layer, of which ~0.5 ms is filling Q and K/V before compute starts; in situ 2800 cycles per 32×64 chunk (qk + exp 1577, pv 1170).

The DDR floor: why 30 % is out of reach for this dataflow

Probe m4 measures the board's DDR as seen from the array: one shim channel reads ~6 GB/s, but any combination of channels and shims saturates at ~10.5 GB/s read, ~10 GB/s write and ~8 GB/s mixed. More shim columns do not add bandwidth.

A lower bound for this dataflow. The ops depend on each other in sequence: attention needs every key, and each GEMM needs the whole previous output. The encoder time is therefore at least the sum, over ops, of each op's own lower bound. Every assumption below favours the bound:

  • Attention, per round. No q-block can finish before all its keys have arrived. A round therefore takes at least the fill that must follow the Q/K/V GEMM, plus (q-blocks − 1) × one q-block's compute.
    • Optimistic case: K and V are prefetched while the Q/K/V GEMM is still running, so only Q (1.18 MB) remains, about 112 µs at 10.5 GB/s.
    • Each q-block is 24 chunks at the best per-chunk cost ever measured: 880 + 273 + 934 = 2087 cycles (probes m5 and m10), with no softmax rescale, mask, copy or finish.
    • Round 1: 112 + 11 × 50 µs. Round 2: 75 + 5 × 50 µs. That is ≥ 0.99 ms per layer, ≥ 3.95 ms for the encoder.
  • Everything else. 77.8 MB read and 55.5 MB written. At the separate peaks (10.5 / 10 GB/s), as if reads and writes never shared the DDR, that is ≥ 13.0 ms. At the measured concurrent rate (~8.3 GB/s), which is what a GEMM streaming its output really sees, it is ≥ 16.0 ms.

A further measurement points the same way. With all attention compute switched off (WE_ATT_NOCOMP), replaying K/V from the memory tiles alone takes 2083 cycles per 32×64 chunk, about 7.9 B/cycle per column. With compute it takes 2532. The current q-block size of 32 therefore sets a K/V stream floor of about 3.6 ms per core for attention. That is close to the compute floor above, and only larger q-blocks would lower it. They do not fit the 64 KB core data memory.

Even with all those favourable assumptions, the bound is 16.95 ms = 29.4 %. At the measured concurrent DDR rate it is ~20 ms = 25 %. Both sit below the 30 % target, so 30 % is not reachable in this dataflow on this board.

Compute alone is just under the target. The per-op core profile (WE_PROF_G/WE_PROF_GOP, attention from WE_PROF_A) puts core (1,3)'s busy time per encoder at 17.2 ms. Part of that is still waiting on data, though. Probe WE_PROF_MAC2 runs every GEMM chunk a second time back to back: the repeat takes 1039–1042 cycles, the same as the standalone kernel, against 1180–1280 for the first run (2550 in the out-projection). With those data stalls removed, pure arithmetic is about 15.8 ms (31 %). So 30 % is reachable only if every op is compute-bound with almost no gaps, which needs far less DDR traffic than today's ~20 ms floor allows.

Probe m11 shows the second half is physically possible. On a 9-column partition, a memory tile outside the mesh streams through the shim row into a mesh memory tile at 7.5 GB/s per stream and 14 GB/s for two in parallel, more than DDR. Activations could therefore live on chip in extra memory-tile columns. That would mean rebuilding the engine's dataflow.

Moving the target would need much less traffic, chiefly keeping FC1's hidden activation on chip. That does not fit the hardware: FC1 + FC2 weights are 2.36 MB against 4 MB of memory tiles, half of which hold activations. The Q/K/V → attention fusion needs 523 KB in a 512 KB memory tile. Smaller cuts are still open (the cross-K/V GEMMs reading their input four times; the 36 padding rows). Together they are about 7 MB, roughly 0.7 ms.

Comparison: the ORT/VitisAI all-AIE decoder

The internal layer-reuse report runs Whisper tiny.en (same architecture, FP16) as seven ONNX graphs through VitisAI, one session per graph call. It measures 43.8 ms for one encoder call and 60.5 s for the JFK decode, of which 53.7 s is session construction. This engine keeps the kernel resident and does the same transcript in about 0.74 s.

9. Build and run it

# 1. weights, goldens, expected tokens (needs the cached tiny.pt + JFK audio)
python3 src/aietensorop/whisperengine/gen_engine.py

# 2. build: two kernel programs + host ELF (~150 MB, weights embedded)
bash src/aietensorop/whisperengine/build.sh eng $PWD/worklocal/whisperengine/build_eng

# 3. run on VEK385 over netboot (ELFs over 94 MB stage at 0x50000000)
python3 script/test/apppaltest.py -y -nonreboot --netload --netload-timeout-ms 1700000 \
    worklocal/whisperengine/build_eng/aout/worklocal/build/host
# look for: "WHISPER transcript MATCHES the PyTorch reference" and "PERF SUMMARY"

Op-level tests: build.sh et1 (GEMM variants, folded LayerNorm), et2 (attention), et3 (conv stem, logits). Host timeline: build with HDEFS=WE_TL; core cycle split: KDEFS=WE_PROF_G or WE_PROF_A.
