1. Summary

  • Everything runs on the AIE except two small steps. All of Whisper-tiny runs on a 4×4 AIE core mesh: encoder convs, attention, MLPs, the decoder's self- and cross-attention, and the 51,865-way logits. The A78 does only the token-embedding lookup and the argmax.
  • Two routes were built. The aiehlc compiler route proves every layer compiles: 147 layers, 24 generated libraries, verified on x86. A hand-written persistent engine is what runs on the board: the kernel is loaded once, and each op is described by an 8 KB header.
  • aiehlc supplies the runtime, the build, the fabric seed and the board loop. That is the AIE runtime library, the kernel/host build scripts, the control-packet plane used to swap the two kernel programs, the conv2dstem routing the fabric started from, and netboot. Everything the engine does per op (kernel, op contract, DMA scheduling, memory-tile programming, weight packing) is hand-written.
  • Memory tiles carry the whole data path. 8 mesh memory tiles replay operands to the cores: activations along rows, weights along columns. 16 storage memory tiles beyond the mesh hold activations between ops (FC1's hidden layer, Q, the attention output, the encoder output). Since memory tiles have no east/west links, those are reached through the shim row.
  • The compiler was not changed to use memory tiles. aiehlc's pipeline has a shim → memtile → core path, but it is switched off, and all memory-tile use in the engine is hand-written (§7).

Route A was the feasibility study. It found and fixed four aiehlc bugs that only show on non-square meshes or non-GEMM layers, and it added aie::RowSpace; details are in GAP_ANALYSIS.md. Its cost model would put the encoder in the seconds:

  • the whole array is programmed per launch, at about 350 ns per register write;
  • the kernels are fp32 scalar;
  • each attention head is its own launch.

Route B keeps aiehlc's runtime and build, and replaces the per-launch model with a resident engine. The rest of this page is Route B.

6. How the memory tiles are used

A memory tile has 512 KB, 6 DMA channels each way, 48 BDs, 64 locks, and stream ports only north and south. Its DMA can also address the memory of the adjacent memory tiles. The engine uses three kinds.

6.1 MT_A: the row operand

  • What it holds. Per op and pass: the sub-op headers (8 KB each), then per 64-row block the A operand (K/48 chunks of 6 KB) and the residual. In attention it holds the 8 Q tiles of its 384 rows.
  • Filled on S2MM1 from DDR (shim MM2S1), or on S2MM3 from a storage tile over a west lane. One BD per block, each releasing that block's lock.
  • Replayed on MM2S0 to the 4 cores of its row as a broadcast: header, then each block once per output tile (twice with hi/lo weights).
    • Two replay BD banks (1–12 and 0, 13–23) alternate per sub-op, so sub-op s+1 is queued while s runs.
    • Each block's replay acquires its lock, so compute starts on block 0 while later blocks still arrive.
  • Double-buffered passes. When two passes fit, MT_A is split into two halves with separate locks, and pass p+1 is filled while pass p computes.
  • Attention. Q arrives q-block by q-block under lock 15, so round 1 starts on q-block 0 before the fill ends. Round 2 reuses the Q tiles round 1 left there.

6.2 MT_B: the column operand

  • GEMM. The column's whole weight slice is loaded once per op, one BD per panel, each releasing its panel lock. It is replayed once per row block, so DDR reads the weights once per op.
  • Attention. MT_B holds the head's KT and V as 64-key chunks of 16 KB, filled row block by row block (each releasing a lock) and replayed once per q-block.
    • In round 2, a column that shares its head with its neighbour does not fetch it again. It replays the K/V straight out of the west neighbour's memory, which a memory-tile DMA addresses at 0x0.

6.3 Storage tiles: activations on chip (columns 5–12)

Probe m4 measured the board's DDR at ~10.5 GB/s read, ~10 GB/s write and ~8 GB/s mixed, whatever the shim count. Moving every activation through DDR therefore cost the engine more than its compute. The storage tiles keep activations on chip between producer and consumer.

Memory tiles have no east/west ports, so the engine routes through the shim row instead. Probe m11 measured this path at 7.5 GB/s per stream and 14 GB/s for two streams. Each mesh row r owns one lane each way:

  • East lane (producer → storage). The row's output shim port is rerouted from its DMA to EAST r, through the shims, then NORTH into the storage tile.
    • The storage tile's S2MM runs in out-of-order mode: each core's output packet carries a BD id in its header, and that BD places the packet. Probe m12 verified this byte for byte.
    • Odd sub-ops use a second BD bank (header word WH_OOO), so sub-op s+1's BDs are armed while s still writes.
  • West lane (storage → consumer). The storage tile's MM2S gathers the consumer's block with a 4-D pattern. It goes SOUTH to the shim, west along lane r, then NORTH into MT_A(r) on S2MM3, one BD per block with a lock release.
  • Route changes. Routes switch per pass at run time (we_st_east, we_st_west); outputs go back to the shims before any DDR-output op.

7. Did the compiler change to use memory tiles?

No. Every memory-tile use above is hand-written, in three places:

  • The fabric. fabric/routing.cc is aiehlc's generated conv2dstem routing with the memory tiles spliced into the input paths by hand.
  • The host. eng/we_host.h writes every memory-tile BD, lock and task queue through the XAie driver, and builds the storage-tile routes at run time.
  • The kernel. eng/kernel.cc consumes whatever the memory tiles replay.

aiehlc's tilinglinalg pipeline does know a shim → memory tile → core path. The dmap → dmaphop lowering (passdmaptodmaphop/dmaptodmaphop.cpp) can insert a memory tile between shim and cores, but RoutingToDmapPass is built with it switched off:

patterns.add<RoutingmovedatabyioConvertdmap>(&ctx, typeconverter, rtopology_, 0 /*op through memtile or not*/);

So the libraries aiehlc generates (conv2dstem, the 24 Whisper layers of Route A) stream shim ↔ core directly. The compiler changes on this branch were the Route A fixes and build support listed in §3, none of them about memory tiles.

To give compiled code what the engine does by hand, the compiler would need:

  • Operand staging: switch on and finish the memory-tile path, with per-block locks and replay banks.
  • Resident schedule: a multi-op schedule instead of one launch per op (GAP_ANALYSIS.md G14).
  • Placement: a pass that puts activations into storage memory tiles and routes producers and consumers over the shim row.

Measured limits

  • DDR: ~10.5 GB/s read, ~10 GB/s write, ~8.3 GB/s mixed for the whole array (m4). With 60 MB read and 31 MB written, that is now a 9–11 ms floor, below the 16.5 ms target.
  • Arithmetic: 15.8 ms of pure core arithmetic per encoder, with data stalls removed (WE_PROF_MAC2: a GEMM chunk run twice back to back takes 1040 cycles). That is just under the 16.5 ms target, so 30 % needs almost every op compute-bound with no gaps, or faster LayerNorm/GELU/attention kernels.
  • Gaps: about 2.7 ms of the 24.3 ms is outside core compute: 8 program swaps (~0.4 ms), per-pass route switching on the shim row (FC1: 12 a layer), attention K/V fills, op hand-overs.
  • Host: register writes ~350 ns and reads ~400 ns, independent of page type (m7). The host now writes only changed BD words and works ahead of the cores, so its time is hidden.

Next steps (paused here)

  • Switch only the differing part of a storage route between passes, instead of all of it (FC1's per-pass switch costs ~100 µs).
  • K and V on chip for attention (needs each column to gather one head from four rows' storage tiles).
  • Faster LayerNorm-apply and GELU loops (chess does not software-pipeline them today).
  • Fewer program swaps (the two programs together need ~18.3 KB of the 16 KB program memory).

Comparison: the ORT/VitisAI all-AIE decoder

The internal layer-reuse report runs Whisper tiny.en (same architecture, FP16) as seven ONNX graphs through VitisAI, one session per graph call. It measures 43.8 ms for one encoder call and 60.5 s for the JFK decode, 53.7 s of it session construction. This engine keeps its kernel resident and produces the same transcript in under 0.7 s.

10. Numerics: why the transcript matches

we_model.py models every rounding point of the engine in PyTorch. It is checked before board changes, produces the goldens, and showed which precision choices keep the transcript:

  • bf16 storage, fp32 accumulation, one rounding per op.
  • LayerNorm folded into the next GEMM: y = rstd·(xW′T − μc) + d, with W′ = γ⊙W, c = ΣkW′, d = b + βWT. The statistics come from the A chunks the core already receives, and the rstd scaling runs on the multiplier as hi/lo bf16 products.
  • Softmax in exp2: log2e/√d is folded into Wq. Integer reference maxima make every rescale exact exponent arithmetic.
  • Exact erf-GELU: a 1280-entry table for every bf16 value with ⅛ ≤ |x| < 4.
  • hi/lo decoder weights: bf16 decoder weights tipped a near-tie at step 14, so W is carried as Whi + Wlo.

The transcript matches PyTorch token for token: "And so my fellow Americans ask not what your country can do for you ask what you can do for your country." Keeping activations on chip changes no arithmetic, only where the bytes live.
