Many conv2d shapes on the AIE: one kernel per fused op, or basic ops?

ResNet-18 int8 has 19 distinct fused conv layers. This page explains how src/aietensorop covers all of them: a hand-tuned fused kernel for the hottest layer (conv2dstem), and for everything else one basic op (convgemm, an int8 GEMM tile) plus TVM's own epilogue. It also explains why the second approach scales and the first does not.

State this page describes (2026-10-10, compile + x86 verified; not run on hardware) deploy_flow.py --aie-offload (default --aie-layers all) offloads every fused op that contains a conv2d. That is 19 layer folders and 20 calls per inference. Each folder gets an aie/, and main.elf calls 19 aie_tvmgen_* entries. All 18 convgemm layers are proven bit-exact on x86 against TVM's untouched function. The stem was proven on the board earlier. run_test.sh --clean passes.

1. The problem: 19 fused conv ops, 11 shapes, 6 tails

After int8 legalization, the zero-point fold and TVM's operator fusion, every conv in the network is one C function that does conv + a fused element-wise tail. They differ in two independent ways.

2. Answer A: one hand kernel per fused op (conv2dstem)

src/aietensorop/conv2dstem/conv2dstem.cc is this approach, done well for one layer:

  • The whole fused op runs on the core. It does im2col, an int32 accumulate, {bias, zp, mult, shift} requantize and clip, then writes uint8. The quant params ride in the weights' padding channel, and one launch does the layer.
  • The geometry is welded in. Every number in the three aie::GemmSpace descriptors is a literal for 230×230×3 → 112×112×64: halo tile 61, stride 56, 4 rounds of 19 rows, and so on. A wall of static_asserts pins the tiling to the shape.
  • Each column keeps its whole filter in core memory (B_local): 16 channels × 196 bytes for the stem.

Scaling this to the table above means 18 more such files. The shape alone forces a redesign, not a re-parameterization, in two places:

  • Memory. A column holding 64 output channels of a 3×3×256 filter needs 64 × 2304 = 147 KB, far over a core tile's 64 KB data memory. The 512-channel layers need 4× that. The kernel must then tile K across rounds and keep partial sums, which is a different kernel.
  • Tiling. 7×7 outputs do not split 4-ways the way 112×112 does, so the descriptors, round counts and halos change per layer.

The tails then multiply the work: six variants, each needing a bit-exact transcription of TVM's arithmetic and constants into the kernel. One wrong rounding term gives plausible but wrong pixels.

When answer A is still right A layer that dominates runtime and has a shape you will keep shipping. Here that is the stem: 12544×64 outputs, the largest feature map. One launch with everything fused is the fastest possible form. That is why layer 01 stays on conv2dstem.

3. Answer B: find what every layer shares

Read the 19 functions side by side and the shared core is obvious. Every one computes acc[n][oc][y][x] = Σ x·w in int32 first, and only then does its tail. So split there:

fused conv layer  =  conv accumulator         (heavy, same for all: int8·int8 → int32)
                   + element-wise tail          (light, different everywhere)

conv accumulator  =  im2col  ;  GEMM  ;  scatter     (im2col/scatter are index shuffles)
GEMM              =  Σ over tiles of a FIXED-shape GEMM tile
  • The AIE does one thing: a fixed 256×64×256 int8 GEMM tile. That is the basic op. It is the same binary for every shape, built once.
  • The host does what is shape-dependent but cheap: NCHWc im2col, splitting any M/N/K into tiles, accumulating K tiles in int32, and scattering back to NCHWc.
  • The tail is not rewritten at all: TVM already generated it, so it is reused (§5).

This is the same factoring a BLAS-backed framework uses (conv → im2col + GEMM). The point here is granularity. The thing implemented on the AIE is chosen to be shape-independent, so the number of AIE kernels is 1, not 19.

The kernel

It is the matmul from example/tileprogram/ccode/simplematmul2.cc, aiehlc's proven GEMM path, with two changes:

A  [256, 256]  RowBA    d1 = 16-row tiles across mesh ROWS,  d2 = K in 64-byte rounds
Bt [ 64, 256]  ColBB    d1 = 16 channels per mesh COL,       d2 = K in 64-byte rounds
C  [256, 64×4 bytes]    16 rows × 16 int32 per core tile, gathered left-to-right

int32_t accum[tile_rows * tile_cols];          // int32: int16 wraps on real weights
for k_round: acquire A chunk; acquire B chunk; accum += A·Bᵀ
emit accum as 4 little-endian bytes per element through the int8 window

Emitting int32 as bytes keeps the proven int8 window/DMA machinery. The C port is just declared 4× wider in d2.

The host side

m = oy*OW + ox          n = occ*ocb + ob          k = ((ky*KW + kx)*ICc + icc)*icb + ib
A[m][k]  = ifm[icc][oy*S+ky][ox*S+kx][ib]      (NCHWc, already zero-point padded by TVM)
Bt[n][k] = wts[occ][icc][ky][kx][ib][ob]       (OIHW{i}i{o}o)
for m0, n0:  for k0:  pack zero-filled tiles → launch → C[m0.., n0..] (+)= tile
acc[occ][oy][ox][ob] = C[m][n]

Zero-filled ragged tiles make any M/N/K exact. A zero row contributes nothing to a dot product. So the stem's K=196, layer 26's M=49 and layer 25's K=4608 all go through the same code.

5. The tail: TVM's own C, transplanted

Hand-writing six tail variants with per-layer literals is where per-op kernels go wrong. So the tail is not written: aie_conv_lib.transplant_tail copies the layer's TVM function and makes two edits.

  1. Delete the MACs. Every conv2d_NCHWc*[i] = conv2d_NCHWc*[i] + (int32)x·(int32)w becomes ;. The activation and weight argument slots are read off these statements.
  2. Redirect the accumulator. In each block ending in an output store ((T*)OUT_1)[IDX] = …, every read of any conv2d_NCHWc* array becomes aie_acc[(IDX)]. The tail is element-wise and the accumulator has the output's NCHWc layout, so the stored element's index is exactly the accumulator element it needs.

Layer 11, before and after (abridged):

// TVM:
int32_t v_ = (int32_t)(((int64_t)((conv2d_NCHWc_global[(cse_var_29 + i4)] + bias[c]) - zp[c] - zp2[c])
                         * (int64_t)mult[c] + (1 << (sh[c]+30))) >> (sh[c]+31)) + 92;
((int32_t*)compute_1)[(((i0_i1_fused_i2_fused * 112) + cse_var_29) + i4)] = … v_ … 1475238455 …;

// aie/tail.c:
int32_t v_ = (int32_t)(((int64_t)((aie_acc[((((i0_i1_fused_i2_fused * 112) + cse_var_29) + i4))] + bias[c]) …
((int32_t*)compute_1)[(((i0_i1_fused_i2_fused * 112) + cse_var_29) + i4)] = … unchanged …;

Every constant, rounding rule and cast is TVM's by construction. The transplant refuses (raises ValueError) rather than guess: no MACs recognised, more than one activation or weight pointer, no store, or any int64 epilogue line still reading an accumulator after the rewrite.

One subtlety found on the way In layers 01, 04, 06 and 08, TVM stages the per-tile register array conv2d_NCHWc_global into a local or workspace conv2d_NCHWc, and the epilogue reads the copy. So "the accumulator" is every array named conv2d_NCHWc*, not only the MAC target. With only the MAC target, those four layers matched zero reads and were refused.

6. Two AIE libraries in one ELF

The stem (libconv2dstem.a) and the basic op (libconvgemm.a) are separate aiehlc builds. Each contains a copy of the AIE runtime plus generated routing(), host_canonicalized(), dskernel_receiver() and g_* globals, so linking both fails with duplicates. Renaming a few symbols is not enough, because aie_runtime.o calls routing(dev) by its fixed name (__Runtime_routing_init). A shared runtime would program one app's stream switches with the other app's routing.

aiehlc_build.isolate_archive gives each library a private runtime:

aarch64-none-elf-ld -r --whole-archive libconvgemm.a -o convgemm_isolated.o   # bind internals
aarch64-none-elf-objcopy --keep-global-symbols=api.txt convgemm_isolated.o     # all else local
ar rcs libconvgemm.a convgemm_isolated.o
# api.txt = conv2d_nchwc_i8 convgemm_i8i32 convgemm_launch_count

Afterwards each library exports only its API. Its undefined symbols are only the XAie driver, libc and libstdc++, and the two partially link together with no duplicate globals.

8. How it is verified (no board)

Hardware was deliberately not used for this step. aie_conv_lib.verify_layer runs on every flow run unless AIE_CONV_VERIFY=0 is set:

  1. It builds one x86 program from the layer's untouched TVM .c, aie/tail.c, aie/entry.c and convgemm_host.h, with the AIE tile replaced by a scalar 256×64×256 loop. Everything around the tile is the real code.
  2. It feeds both functions the same inputs: real parameters from resnet18_params.bin, plus random activations over each dtype's full range.
  3. It compares every output byte. The result is 18/18 layers identical, e.g. 200704/200704 output bytes identical, recorded in partition.json and checked by run_test.sh.

That proves im2col, tiling, K accumulation, scatter and the transplanted tail. It does not prove the AIE tile on hardware, i.e. the int32-as-bytes C window and the DMA layout. That is the next board run: apppaltest.py on main.elf should print one ENTER/EXIT pair per layer and match main_local.elf's top-5.

9. Cost model and where to go next

Launches per inference: the stem's 1, plus Σ ⌈M/256⌉·⌈N/64⌉·⌈K/256⌉ over the 19 convgemm calls (layer 04 runs twice), which is 952 tile launches. Each one currently does aieSetDevice + partition + routing + DMA BD setup. At ~372 ns per XAie_Write32 (doc/performance/register_write_cost.md), the setup will outweigh the 4.2 M MACs a tile computes (256·64·256). The basic-op approach buys generality; these steps buy the speed back, roughly in order of payoff:

  1. Keep the partition and routing alive across launches. Only re-arm BDs per tile (the same routing every time), or move to control-packet BD writes (~2.9 ns per write).
  2. Bigger tile, weight-stationary. Load Bt once per (n0, k0) and stream all M tiles past it. This cuts launches by ⌈M/256⌉ for the early layers.
  3. A second basic op: the per-channel requantize epilogue on the core. It returns int8 instead of int32, so 4× less output DMA, for the tail variant A layers whose tail is only requant + clip. Keep the transplant for the rest.
  4. im2col on the DMA. aiehlc already has aie::Im2col::Dma with halo descriptors (the stem uses it). Generating those descriptors from convgemm_geom removes the host im2col copy. That is the step from a "GEMM basic op" to a "parameterized conv basic op".
  5. Promote a hot layer to answer A when profiling says so, as was done for the stem.
